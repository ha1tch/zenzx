| 1 | Model skeleton, ROM loading, chunk-0 banking, boot | ✓ | Verified end to end 2026-08-17 (`TestTS2068Stage1Boot`): boots to copyright screen, keyboard input works, `PRINT 9` [ENTER] produces correct output and the real "0 OK" ready prompt. | 2 | Frame timing (NTSC clock/frame rate) | ✓ | Verified 2026-08-17 (`TestTS2068Stage2Timing`): `cyclesPerFrame`/`interruptCycles` are now per-`ZenZX`-instance fields (58688/58594 for TS2068, computed precisely from 3528000Hz/60.1145Hz), threaded through `RunFrame`, `display.go`'s border-stripe timing (both GUI and headless stubs), and snapshot cycle bookkeeping. Every non-TS2068 model verified unaffected -- identical values to the PAL constants they replace. Deliberately did not touch `CPUFrequency`/`FramesPerSecond` or `audio_oto.go`: TS2068 audio isn't implemented yet (Stage 4), so nothing currently depends on those being correct for TS2068; revisit when Stage 4 lands, since AY pitch generation will need the true clock. |
| 3 | `CHNG_VID` (real ROM code, substrate verification) | ✓ | Rescoped during this session, per direct correction: real TS2068 software engaged hi-colour mode with a direct `OUT` to port `FFH`, not the documented Extension ROM `CHNG_VID` service -- and the hardware has no auto-clear mechanism; real software (and this test) had to clear the hi-colour plane by hand. "CHNG_VID support" in this scope means the emulator now dynamically switches its active video renderer on the guest's own port write (`SpectrumIO.onTS2068VideoModeChange`), not only via the static `-ns-graphics` host flag. Verified end to end (`TestTS2068Stage3DynamicVideoMode`): garbage seeded in the hi-colour plane beforehand, program clears both planes itself, writes mode 2 directly to port FFH, pokes 8 stripes by hand (not BASIC PLOT/DRAW, which never touch the hi-colour attribute plane on real hardware), renderer switches automatically, correct colours confirmed both by memory assertion and by rendering through the real `mode-timex-001-hicolour` renderer. Full real-ROM-service route (`IFRTN`/`CALL_BANK`/`REMGSZ`/`OPDFIL`) was attempted first and abandoned after extensive tracing hit a genuine, uncharacterized divergence partway through the relocation's clear-loop -- confirmed NOT caused by chunk-0 banking (works correctly, traced directly) or the two loops initially suspected (both genuinely progress to correct completion, confirmed via direct register tracing) -- root cause undiagnosed, left as a known gap rather than pursued further given real software didn't depend on that path anyway. |
| 4 | AY sound chip ports (`F5`/`F6`) and joystick | ✓ | Verified 2026-08-17 (`TestTS2068AYPorts`, `TestTS2068JoystickPorts`). AY: `F5H`/`F6H` reuse the same underlying AY chip and `ayRegister` field the existing 128K-style ports (`0xFFFD`/`0xBFFD`) already use -- purely a new dispatch path, no new AY emulation. Confirmed low-byte-only decode (upper address byte from whatever's in `A` during a single-byte `OUT` is correctly ignored, matching the SCLD's full 8-bit port decode) and confirmed a real AY register-width quirk (register 3, Coarse Tune B, genuinely 4 bits on real hardware) flows through correctly rather than being papered over. Joystick: register 14 read via `F6H`, address bit 8/9 selecting port 1/2, active low per Table 2.4.4-1 -- a different polarity from Kempston Joystick's active-high and a different bit layout from AMX Mouse's buttons, both already in the codebase. Always active for this model (TS2068's own built-in hardware, not an optional `-joystick`-style peripheral) via a new `handleTS2068JoystickInput`, sharing a refactored `readGamepadState` helper with the existing Kempston/Sinclair path -- gamepad 0 drives port 1, gamepad 1 (if present) drives port 2. |
| 5 | Tape I/O (accurate mode; fast-mode trap if feasible) | ✓ | Both halves verified 2026-08-17 via real ROM execution, not assumption. **Fast mode**: direct disassembly of `rom/ts2068-1.rom` found `R_TAPE`/`W_TAPE` are a byte-for-byte relocated copy of the standard 48K ROM's `LD-BYTES`/`SA-BYTES` (constant offset `0x045A`) -- so the newly-hardened `trapLoad` (T-02) is reused unchanged; only the trap addresses (`0x0112`, matching the same "after real ROM housekeeping, before the slow pulse call" positioning as the standard trap) and a new chunk-0-aware context check (`isTS2068ExtensionROMActive`) differ. `TestTS2068FastLoaderRealROMIntegration` proves it via a hand-assembled program that engages chunk-0 Extension ROM banking itself and `CALL`s the real `R_TAPE` entry directly. **Accurate mode**: confirmed to genuinely work with zero TS2068-specific code, exactly as the plan predicted -- `TestTS2068AccurateModeRealROMIntegration` runs a full, real, pulse-by-pulse load through the actual ROM (809,629 CPU steps, ~30ms wall-clock, not impractically slow as initially worried). Save-side (`W_TAPE`) correctly declines, matching the standard model's `SA-BYTES` scope (T-02): zenzx has no tape-save capture to hook into for either. |
| 6 | Memory contention | ✗ | Postponed, 2026-08-17. Investigation found no contention modeling exists for *any* model, not just TS2068 (checked directly in both zenzx and zen80, not assumed) -- meaning this was never really "TS2068's own pattern vs the standard one," since there is no standard-model baseline to diverge from. Spun out into a general, non-TS2068-scoped register item (T-16) rather than built one-off here, which would have left TS2068 more cycle-accurate than the models it shares a substrate with. Affects cycle-exact border effects and timing-sensitive demos only -- not ordinary program correctness, and everything verified across Stages 1-5 already works without it. |

## Deviations from the plan

- **Stage 3, 2026-08-17**: the plan specified verifying the real
  Extension ROM `CHNG_VID` service end to end (via `IFRTN`). Rescoped,
  per direct correction, to dynamic port-`FFH`-driven renderer switching
  plus manual framebuffer clearing -- matching how real TS2068 software
  actually engaged hi-colour mode, not the documented service call.
  The full service-call route hit a genuine, undiagnosed divergence
  during `OPDFIL`'s relocation and was abandoned rather than pursued
  further, since real software didn't depend on that path either. See
  the Stage 3 row above for detail.
- **Stage 6, 2026-08-17**: postponed rather than implemented, and
  rescoped from "TS2068's own pattern" to a general, non-TS2068 register
  item (T-16), once investigation found no baseline contention modeling
  exists anywhere in the project to diverge from. See the Stage 6 row
  above for detail.
